- **Before you deploy this release, point Uptime Kuma at `https://<domain>/health`, and move every other direct user of port 8000 or 8003 (a Home Assistant sensor, a script) to the nginx route `/muma/api/` or the Docker network.** `music-manager` publishes ports 8000 and 8003 on `127.0.0.1` only (`MUSIC_MANAGER_BIND_ADDRESS`, default `127.0.0.1`). Before, they listened on every interface, so the LAN and the tailnet reached the API without nginx in front. A call from another machine to `http://<host>:8000` now fails to connect. nginx, LMS and the workers call `music-manager:8000` over the `music-management_db` network and are not affected. (issue #218)
- The login rate limit believes `X-Forwarded-For` only from loopback and the Docker networks of the `music-manager` container. The default of `AUTH_TRUSTED_PROXIES` is `127.0.0.0/8,::1/128,connected`, where `connected` is read from the container's routing table. Before, it was the three private ranges, so any host on the LAN could name a new client address with every guess and get a new per-client bucket each time. The per-account limit of 50 a minute was not affected.

- `GET /health` is public through nginx at `https://<domain>/health` (an exact-match `location` in `reverse-proxy.conf`), so an outside monitor needs no port of its own. Without a valid `X-API-Key` the body is `status` and `source_url` only; the version, database, thread and heartbeat fields need the system key or a user's key. The status code is 200 or 503 either way, so Uptime Kuma and the container healthcheck need no key. `post-deploy-verify.sh` reads the version with the system key from the container's environment, and `tools/muma_mcp` sends its key.
