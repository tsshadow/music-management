Playlists with a face

The web UI already has the Spotify tokens. The Android app and Android Auto show the same playlists as text rows with a generic icon. This proposal gives every playlist a cover that the app makes itself, from the genre, the festival or the DJ. That way one image system serves the web, the phone and the car.

One engine, three families

The cover is rendered locally on a 320×320dp canvas: a duotone photo, a color surface that carries the genre, and a wordmark. The color is not chosen but derived. The same genre name always gives the same color, on every device.

What changes compared to now

NowProposal
Genre is a text line in a listGenre is a tile with its own color and wordmark, recognizable at a distance
A playlist without a cover gets the music-staff iconPlaylistArt always renders something, from name + type
Rows are text lists stacked on each otherHorizontal strips like the web UI, cover first
Every list has the same grey tintColor comes from the genre, deterministic, so stable across devices

The color is derived, not chosen

// Fixed table for the genres the collection carries, hash for the rest.
object GenrePalette {
    private val known = mapOf(
        "hardstyle" to 0xFFFF4D00,
        "hardcore"  to 0xFFE5002B,
        "techno"    to 0xFF00E0C7,
        "trance"    to 0xFF7B2DFF,
        "house"     to 0xFFFFB400,
    )

    fun tintFor(name: String): Int {
        val key = name.lowercase().trim()
        known[key]?.let { return it.toInt() }
        // Same name, same color, on the phone and in the car.
        val hue = (key.hashCode().absoluteValue % 360).toFloat()
        return Color.HSVToColor(floatArrayOf(hue, 0.82f, 0.95f))
    }
}

The same table should be in the web UI, otherwise Hardstyle is orange there and magenta here. Put it in the server response next to the genre name, so that neither client needs to know it.

In the car

Android Auto renders what the app delivers. Right now MuMa delivers no content-style hint and no artwork for browsable items. So the main menu becomes a text list with default icons. With a grid hint and an artwork URI it becomes this same picture, without a screen design for the car existing.

The code that turns this on

// MediaItemConverter.kt: these constants are not in it yet.
private const val CONTENT_STYLE_BROWSABLE =
    "android.media.browse.CONTENT_STYLE_BROWSABLE_HINT"
private const val CONTENT_STYLE_PLAYABLE =
    "android.media.browse.CONTENT_STYLE_PLAYABLE_HINT"
private const val GRID_ITEM = 2
private const val LIST_ITEM = 1

extras.putInt(CONTENT_STYLE_BROWSABLE, GRID_ITEM)  // genres, festivals, DJs
extras.putInt(CONTENT_STYLE_PLAYABLE,  LIST_ITEM)  // tracks and sets
// The cover comes from the same content provider as album art,
// so Auto may load it without network permissions.
val art = AlbumArtContentProvider.mapPlaylistArtUri(
    kind = PlaylistArtKind.GENRE,
    key  = genre.name,
)

buildMediaItem(
    title       = genre.name,
    mediaId     = "genre|" + genre.name,
    isBrowsable = true,
    isPlayable  = false,
    imageUri    = art,
)

Without CONTENT_STYLE_BROWSABLE_HINT, Auto mostly ignores the artwork URI for browsable items. It falls back to a list with a small icon. Rendering the cover without setting the hint therefore makes no visible difference.

Build order

Each step is valuable on its own and can be released on its own.

StepWhatWhy first
1 GenrePalette + PlaylistArtRenderer in the app, and send the tint from the server next to the genre name Without a shared color source, web and app drift apart
2 Content-style hints in MediaItemConverter Two lines; makes Auto a grid right away, even with the current artwork
3 Artwork URI for browsable items in MediaLibraryBrowser Fills the grid that step 2 opens
4 Turn the home strips on the phone cover-first Most of the work, and it benefits from steps 1 to 3
5 Link family B to real festival images where they exist Optional; the generated cover is already complete
